# 가상 테스트 자료

`receipts/`의 영수증 10장(`receipt-r01.png`~`receipt-r10.png`)과 정답(`ground-truth.json`)은 native-batch-import 실험의 생성기로 만든 가상 일본어 영수증이다. 가게·주소·전화·카드·회원·예약 번호와 EXIF·GPS·설명 메타데이터가 모두 가상 값이며 `SYNTHETIC-ORIGINAL-METADATA rNN` 표지를 담고 있다. r10은 초점을 일부러 흐린 사진이라 실제 OCR이 읽지 못한다. 정답에는 날짜·합계·가게, 각 줄의 위치, 가려야 할 민감한 줄의 위치가 있다.

- 앱 번들에는 들어가지 않는다. 단위 테스트(iOS `ReceiptImport` 패키지, Android JVM)와 시뮬레이터·에뮬레이터 E2E만 쓴다.
- `settlement/examples.json`: 정산 공통 예제(가상 값). `pair_splits`(둘이 반씩), `settlement`(계약 시험의 여행방), `krw_conversions`(엔화 환산: 취득 원가·기준환율 예상, 원 단위 반올림). 서버 계약 시험과 두 앱 단위 테스트가 같이 읽는다.
- `settlement/fx-responses/`: 로컬 서버에서 받은 실제 응답(장부·미리보기·v1·v2 확정본, 가상 계정·가상 시험 환율). `scripts/capture-fx-responses.py`로 다시 만든다. 정정 상태(ADR-0009)의 장부·미리보기·확정 거절 응답(`ledger-correction.json`·`preview-correction.json`·`finalize-correction-refused.json`)은 `scripts/capture-fx-correction-responses.py`로 다시 만든다. 계정 ID는 고정한 가상 UUID로 바꿨다. 두 앱의 응답 해석 시험이 읽는다.
- `settlement/proposal-responses/`: [ADR-0011](../../docs/adr/0011-cross-device-item-share-proposals.md)의 제안 보내기 응답과 방장·올린 회원·다른 회원의 장부 응답이다. 두 앱의 응답 해석 시험이 읽는다. `mise run local:up` 뒤 저장소 루트에서 `python3 -I scripts/capture-proposal-responses.py`를 실행하면 새 가상 여행방에서 응답을 받아 고정 파일을 다시 만든다. 계정 ID는 고정한 가상 UUID로 바꾼다.
- `masking/`: 가림 보강 시험 자료. `make_mask_variants.py`(표준 라이브러리만)가 `receipts/`의 r01–r04를 기울이거나(+15°, −8°, +3°) 흐리게(σ 2.2) 한 PNG와, 그 사진에서 기기 OCR이 보인 실패(라벨과 번호가 따로 읽힘, 깨진 라벨, 번호를 못 읽음, 줄을 통째로 놓침)를 흉내 낸 OCR 줄·정답 줄 모서리(`variants.json`)를 만든다. Android JVM 시험 `MaskHardeningTest`가 읽는다.
  - `masking/common-policy.json`은 두 앱의 공통 가림 계약 예제다. OCR 줄과 이미지 크기, 선택적인 모서리·줄 안 번호 상자·재OCR 입력을 기록한다. 상자 `[left, top, right, bottom]`의 원점은 사진 왼쪽 위이며 오른쪽·아래는 범위에서 제외한다. `expect.masked`와 `expect.visible`은 이름이 붙은 잉크 범위다. 두 테스트는 범위 안의 모든 픽셀 중심을 실제 가림 모양과 대조하고 `needsReview`와 `reasons`를 함께 확인한다. `reviews`는 교차 검토 항목이나 계약을 가리킨다.
  - 타일 예제는 전체 사진 좌표의 `lines`와 타일 로컬 좌표의 `tiles`를 함께 둔다. Android는 `OcrTiles.merge`를 거치고 iOS는 Vision에서 전체 사진 좌표로 변환된 줄을 입력으로 받는다. 실제 Vision 타일 인식은 패키지의 별도 이미지 시험에서 확인한다. 앱별 알려진 실패는 각 테스트에서 항목과 단언 단위로 보관해 새 실패와 해결된 실패를 모두 드러낸다.
- `korean/`: 한국어 입력([ADR-0013](../../docs/adr/0013-android-korean-ocr.md)). `make_korean_inputs.swift`(macOS CoreText, Apple SD Gothic Neo·Hiragino Sans)가 만든 가상 사진 4장과 정답(`ground-truth.json`, `receipts/`와 같은 형식에 `kind`·`currency`·`protected`를 더함)이다. `input-k01.png` 숙소 예약 화면 캡처(원화 ₩265,100, 예약번호·연락처·카드, 지출 날짜는 체크인이 아니라 결제일 2026-10-20), `k02` 간편결제 내역 화면(38,500원, 카드·승인 번호, `2026년 11월 4일` 날짜), `k03` 한국어 영수증(합계 6,900원, 전화·카드·승인 번호), `k04` 한국어 해외 결제 화면에 일본어 가게·상품 줄 2줄이 섞인 것(합계 ¥2,480, 원화 환산 줄 별도)이다. 앱·가게·번호는 모두 가상 값이고 사진 설명에 `SYNTHETIC-ORIGINAL-METADATA kNN` 표지가 있다. 화면의 "라벨 ……… 값" 행은 값 칸만 가릴 대상(`sensitive`)으로 적었다. `protected`는 가리면 안 되는 금액·날짜 행이다.
  - `korean/language-choice.json`: 두 앱의 언어 선택 공통 예제(일본어·한국어 결과의 줄 글자와 신뢰도 → 고를 쪽). 세 사례는 Android ML Kit이 실제로 낸 결과를 옮겼고, 보충 평면 한자·특수 공백 사례가 글자 수 정의(코드 포인트, White_Space 25자)를 고정한다.
  - `korean/proposal-fields.json`: 두 앱의 합계·통화·날짜 공통 예제(OCR 줄 → 금액·통화·날짜 또는 실패).
- `check_artifact.py`: 기기에서 꺼낸 원본과 가림 사본을 정답과 비교한다(표준 라이브러리 PNG 디코더). `receipts/`와 `korean/`의 정답을 원본 바이트로 찾는다. 원본을 사본으로 넣으면 실패하는 것으로 검사기 자체를 확인했다.
- `items/`: 품목별 나누기 자료([ADR-0010](../../docs/adr/0010-on-device-item-split.md)). `receipt-i01.png`(가상 居酒屋, 품목 5개·내세 합계 3,500엔·수량 표시 1줄)와 `receipt-i02.png`(가상 マート, 품목 3개·할인 -50·소계 648·세금 51·합계 699엔)는 `make_item_receipts.swift`(macOS CoreText, Hiragino Sans)로 만든 가상 영수증이다. 사진 앱 설명에 `SYNTHETIC-ITEMS-METADATA iNN` 표지가 있다. `examples.json`은 두 앱이 같이 읽는 공통 예제다: `extraction`(OCR 줄 → 품목·요약·표시), `real_ocr`(실제 OCR로 읽은 두 장의 정답), `allocation`(사람마다 원 몫·남은 원·문제, 기대값은 손으로 계산). `check_apple_translation.swift`는 macOS 호스트에서 Apple Translation 기기 번역을 앱과 같은 API로 확인한다.
