# Android 한국어 OCR과 두 앱의 언어 선택 규칙

상태: accepted (2026-11-26, 사용자 합의). [ADR-0005](0005-receipt-review-and-mask-correction.md)의 "현재 Android 구현"에서 한국어 OCR 모델을 포함하지 않는다는 줄과 "현재 iOS 구현"의 한국어 인식 확인 조건(가나가 적은 사진만)을 대체한다.

제품 범위의 결제 화면 캡처(숙소 예약 화면, 항공권 결제 메일, 토스 인출·환전 내역)는 한국어다. iOS는 Vision에 `ko-KR`을 넣어 읽었지만 Android는 ML Kit 일본어 모델만 있어 한국어 화면에서 합계와 한국어 라벨(승인번호 등)을 읽지 못했다.

## 결정

- **Android에 ML Kit 번들 한국어 모델을 넣는다.** `com.google.mlkit:text-recognition-korean` 16.0.1(일본어 모델과 같은 판·같은 공통 엔진). 여행 중 네트워크가 약할 수 있어 Play 서비스 동적 다운로드는 쓰지 않는다. release APK는 54,582,043 → 55,106,643 B(+524,600 B, +0.96%)다. 늘어난 것은 ABI와 무관한 모델 자산이고 ABI별 네이티브 라이브러리는 그대로다.
- **사진마다 두 언어로 모두 읽고 두 앱 같은 규칙으로 고른다.** Android는 일본어·한국어 모델, iOS는 일본어·영어 우선 읽기와 한국어를 포함한 자동 감지 읽기다. 점수는 줄마다 (공백을 뺀 유니코드 코드 포인트 수 × 엔진 줄 신뢰도)의 합이고, 공백은 유니코드 White_Space 25자로 두 앱에서 직접 정한다(UTF-16 단위나 플랫폼 공백 API를 쓰면 보충 평면 한자·특수 공백에서 두 앱의 선택이 갈렸다). 한국어 결과의 한글 줄이 2줄 이상이고 점수가 일본어 결과보다 높을 때만 한국어 결과를 쓰고, 같으면 일본어(예전 동작)다. 각 모델(읽기)의 준비·읽기 실패는 따로 처리해 한쪽만 성공하면 그 결과를 쓰고, 둘 다 실패하면 실패로 남긴다. 취소(코루틴 취소·스레드 인터럽트, iOS 작업 취소)는 다른 모델로 넘어가지 않고 그대로 멈춘다. 규칙은 공통 표 `apps/fixtures/korean/language-choice.json`으로 두 앱이 함께 시험한다. 신뢰도의 척도는 엔진마다 다르므로 같은 것은 식과 조건이고 문턱값을 엔진끼리 비교하지 않는다.
- **조건부로 한 번 더 읽지 않는다.** 일본어 결과만 보고 한국어 읽기를 건너뛰는 조건을 찾지 못했다. 가상 입력 448장(일본어 336, 한국어 112)에서 ML Kit 일본어 모델은 한국어 화면의 한글을 가나·한자로 잘못 읽어 기준 4장에서 가나 줄을 2~4줄 만들었고, 한국어 모델은 일본어 영수증에서 한글 줄을 최대 8줄 만들었다. iOS의 예전 조건(일본어 읽기의 가나 줄 2줄 미만)은 한국어 112장 중 78장만 한국어로 골랐고, 일본어 가게·상품 줄이 2줄 섞인 한국어 결제 화면(k04)을 놓쳤다. 한국어 입력을 놓치면 한국어 라벨을 읽지 못해 가림이 약해지므로 처리 시간을 더 쓴다.
- **합계·통화·날짜를 한국어 입력에 맞춘다(두 앱 같은 규칙, 공통 표 `proposal-fields.json`).** 합계 낱말에 `합계`·`결제 금액`·`총 금액`을 더하고 `小計`·`소계` 줄은 뺀다. 통화는 합계를 읽은 글자의 표시로 정한다. 표시는 숫자 뒤 `円`·`원`, 숫자 앞 `¥`·`₩`, 앞이 영숫자가 아닌 `JPY`·`KRW`(뒤에 금액이 붙어도 된다)와 독립된 금액 토큰 바로 뒤의 `JPY`·`KRW`(`2480KRW`는 되고 `A1KRW`는 아니다), 숫자 바로 앞 `W`(ML Kit의 `₩` 오독)뿐이고, `회원번호`의 `원`이나 상품 코드 `A1KRW2`처럼 금액과 무관한 글자는 세지 않는다. 표시가 없거나 둘 다면 표시가 붙은 줄이 많은 쪽, 그래도 같으면 한글 줄이 2줄 이상일 때 KRW, 아니면 JPY다. 날짜는 `년`·`월` 구분도 받고, `결제일`·`결제일시`·`결제 일자` 라벨(라벨 끝을 확인해 `결제 일정`은 아니다) 줄의 날짜나 그 행 오른쪽 값을 먼저 쓴다(숙소 화면의 체크인 날짜가 먼저 나와도 결제일을 지출 날짜로 한다). 없으면 위에서부터 첫 날짜다.
- **한국어 가림 라벨을 두 앱에서 맞춘다.** 판단이 애매하면 가리거나 "가림 확인 필요"를 남긴다(누락보다 과잉 가림). 가게명·주소·레지 ID·사업자 등록번호·가맹점 번호와 가격·날짜·합계는 가리지 않는다.
  - `카드번호`·`승인번호`·`회원번호`·`예약번호`처럼 "번호"와 묶은 라벨과 `전화`·`연락처`는 그대로 라벨이다.
  - "번호"가 빠졌거나 따로 읽힌 낱말(`카드`·`승인`·`회원`·`예약`·`번호`)은 바로 뒤에 숫자 2자리 이상이 든 번호 값(`승인 4938`·`승인 46`·`예약: AB12`)이 붙으면 라벨이다. 줄이 그 낱말로 끝나면(`승인`, `결제 카드`) 값이 따로 읽힌 독립 라벨로 보고, 강한 라벨과 같이 같은 행·바로 다음 행에서 값을 찾아 가리며 못 찾으면 확인을 안내한다.
  - 문구 속 낱말(`예약 확정`, `가상카드 일시불`, `예약 2명`)은 라벨이 아니다. `사업자(등록)·등록·가맹점 번호`는 띄어쓰기와 상관없이 가게 정보로 뺀다.
- **같은 행의 값은 그 값의 중심보다 시작점이 앞서는 라벨·필드명 중 가장 가까운 것의 값이다(두 앱).** 다열 행(`承認番号` 값 | `会員番号` 값)에서 다른 항목의 번호를 짝으로 잡지 않고, OCR 상자가 겹쳐도 같다. 다른 필드명(수량·금액·소계·합계·결제수단·상태 등)의 값(`결제 금액 | 1200`, `수량 | 120`)은 같은 행이든 다음 행이든 그 필드의 것으로 보아 가리지 않는다. 가격·날짜 상자는 경계가 아니어서 인라인 값 뒤 조각(`承認番号 493` | `¥320` | `38`)은 계속 묶고 가격은 묶지 않는다. 한 자리 조각 묶음(`承認番号 012` | `3` `4` `5`)은 다른 라벨의 시작점이나 보호 상자에서 끝난다. 다른 라벨 칸이라 건너뛴 짧은 번호, 묶을 근거 없이 라벨 가까이 남은 한 자리 숫자가 끝까지 가려지지 않으면 확인을 안내한다. 다른 라벨 줄 안의 번호는 이 라벨의 짝이 아니다.
- **가림 도형은 두 불변식으로 정의한다(두 앱, 오케스트레이터 결정 2026-11-27).**
  1. 가려야 할 민감 OCR 상자는 기울었든 아니든 항상 완전히 덮고, 어떤 이유로도 줄이지 않는다. 민감 OCR 상자는 번호(숫자·가림 기호)가 든 고른 줄이고, 섞인 줄은 번호 부분 상자다. Android는 띠가 덮으려는 번호 조각 중 보존 상자와 겹친 것도 넣는다.
  2. 민감 상자 밖에 더한 여백은 보존 상자 중 민감 상자 밖 픽셀을 덮지 않는다. 보존 상자는 가격·금액·날짜·합계, 가게 정보(가맹점·사업자·등록 번호, 레지), 필드명과 그 값이다.
  - 구현은 칠하는 순서다. 여백을 포함한 띠·도형(검정)을 칠하고, 보존 상자를 원본 픽셀로 되돌리고, 민감 상자를 검정으로 다시 칠한다. 사용자가 켠 줄의 띠와 직접 더한 띠는 마지막에 칠한다. Android `Masking.shapes`의 `MaskShape.Restore`, iOS `MaskPlan`이다.
  - 숫자 없는 라벨 줄(`승인`, `결제 카드`)은 민감 값이 아니라 여백처럼 다룬다. 보존 잉크가 번호의 OCR 상자 안에 있으면 상자 좌표만으로는 둘 다 지킬 수 없어 번호를 가린다("상자 겹침 불가피").
  - 4차의 여백 축소·겹침 안내·기울기 예외는 지웠다.
- **차등 검사로 회귀를 막는다.** 공통 가림 표 전체(세 독립 검토의 반례와 무작위 검사의 최소화 사례 포함)와 시드 고정 무작위 배치(시드 세 개, 각 2,400배치: 일·한·영 강한/약한 라벨, 인라인 값, 1~4자리 조각, 다른 라벨·필드와 값, 가격·수량·날짜·합계·가게 번호, 상자 겹침·간격)를 main(e68cce6), 7196433, 새 코드의 두 앱 가림 함수로 돌려 비교했다. 시드는 20261127·20261128·20261129·7777 네 개다. 새 코드가 이전 판이 보호하던 민감 값을 안내 없이 남기는 경우와, 두 이전 판이 모두 0픽셀이던 보존 범위를 새로 1픽셀이라도 가리는 경우가 모두 0건이다. 예외는 덮인 보존 픽셀이 그 민감 값이 속한 OCR 줄 상자 안에만 있는 경우로, "상자 겹침 불가피"로 따로 센다. 두 불변식은 같은 네 시드 전 배치에서 두 앱 모두 픽셀 단위로 직접 확인했다(위반 0). 세 판이 모두 놓치는 경우는 이슈 #8로 넘긴다.
- **iOS 처리기는 취소를 OCR 큐까지 전한다.** 취소되면 새 사진을 가져오지 않고, 동기 Vision 읽기에는 신호를 넘겨 모델·타일 사이에서 멈추며, 상태를 쓰기 전에 다시 확인한다. 읽던 사진은 끝난 것으로 쓰지 않고 디스크에 처리 중으로 남겨 다음에 처리기를 만들 때 대기열로 돌아간다(기존 복구 규칙, Android의 `runInterruptible` 동작과 같다).

## 대가

- 모든 사진을 두 번 읽는다. 이미지당 인식 시간(중앙값, 일본어 기준 11장)은 Android 에뮬레이터에서 32.1 → 45.5 ms, iOS 시뮬레이터에서 568 → 1,159 ms다(한국어 4장은 Android 40.2 → 69.8 ms, iOS 960 → 964 ms, 측정마다 수십~백여 ms 흔들린다). 사진 10장을 동시 2장으로 처리하면 iOS에서 약 3초가 늘어난다.
- APK가 0.5 MB 늘었다.
- 엔진 오독이 남는다. iOS 한국어 포함 읽기는 k04의 `¥2,480`을 `·2,480`으로 읽어 통화가 KRW로 제안되고(검토 화면에서 고친다), k03 영수증의 `합계` 라벨과 `6,900원`의 끝 글자를 놓쳐 합계를 찾지 못한다(직접 입력). iOS는 흐린 한국어 변형 3장에서 카드 번호 오독으로 번호를 가리지 못했고, 세 장 모두 "가림 확인 필요" 안내가 붙었다. Android는 한국어 기준 4장의 금액·통화·날짜를 모두 맞혔지만 긴 화면의 타일 겹침에서 같은 날짜를 `2026.10,20`으로 한 번 더 읽어 그 줄을 번호로 가리거나, `₩265,100`을 `W265100`으로 읽어 합계 줄을 가리는 경우가 변형 사진에서 있었다(보호 줄 과잉 가림 9/360).

## 확인할 것

- 실제 기기에서의 처리 시간과 배터리, 실제 결제 화면·메일 캡처에서의 선택 결과. iOS의 두 번 읽기 비용이 크면 한국어 포함 읽기 하나로 줄이는 방안(일본어 336장 중 285장은 두 읽기 결과가 같았다)을 따로 검증한다.
