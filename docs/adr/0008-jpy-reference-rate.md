# 엔화 지출의 원화: 실제 청구액 → 환전 원가 → 한국은행 기준환율 예상

상태: accepted (2026-11-24, 로컬 슬라이스). "나중에 들어온 고시값은 … `fx_superseded`로만 알린다"와 남은 질문 "확정을 막을지"는 superseded by [ADR-0009](0009-fx-correction-before-finalize.md)(정정된 포함 예상액은 방장이 고정 금액 유지나 새 예상 적용을 고를 때까지 확정하지 않는다. 출처 종류를 포함한 하나의 비교). [ADR-0001](0001-krw-conversion.md)의 미정 중 "기준환율의 데이터 제공처, 미공표일 처리, 환산액의 원 단위 반올림"을 엔화(JPY)에 한해 정한다. [ADR-0006](0006-room-settlement.md)의 "원화는 확정된 값만 받는다 … 기준환율 자동 환산은 없다"는 엔화에 한해 대신한다(다른 외화는 그대로 실제 청구액만).

사용자가 엔화→원화 범위를 승인했다. 원화 근거는 ADR-0001의 순서 그대로다. 확인한 실제 원화 청구액이 먼저고, 없으면 증빙으로 확인한 외화 취득 원가, 둘 다 없을 때만 한국은행 ECOS 기준환율로 계산한 예상액을 쓴다. 예상액은 실제처럼 보이면 안 된다. 서버는 `supabase/migrations/20261124130000_jpy_reference_rate.sql`, 받기 어댑터는 `scripts/ecos-fx.py`, 앱은 두 앱의 `Features/Settlement`(iOS)·`feature/settlement`(Android)다.

## 결정

- **방장이 기준을 고르고 승인한다.** 검토 요청에 `p_krw_basis`(`verified_krw_charge` | `acquisition_cost` | `reference_rate_estimate`)와 근거를 함께 보낸다. 서버는 기준을 스스로 고르지 않는다. 근거가 맞지 않으면 포함하지 않는다(`basis_invalid`, `krw_unverified`). 기준을 정할 수 없으면 지금처럼 확인 필요로 두거나 보류한다. 기준을 보내지 않은 예전 요청은 예전과 같다(외화 = 실제 청구액). 요청 지문도 같아서 이 마이그레이션 전에 보낸 검토의 재시도가 그대로 수렴한다.
- **기준환율 출처: ECOS 731Y001 / 0000002.** 통계표 "3.1.1.1. 주요국 통화의 대원화환율"(주기 D, 출처 서울외국환중개)의 항목 "원/일본엔(100엔)", 단위 "원"이다. 값은 100엔당 원이다(`quote_unit` = 100). 2026-11-24에 ECOS `StatisticTableList`·`StatisticItemList`로 확인했다(항목 시작 1977-04-01). 공개 시험 키 `sample`로 실제 `StatisticSearch` 응답도 받았다. 값은 소수 둘째 자리 글자(`"833.45"`)였고, 주말인 11-14·15·21·22에는 값이 없었다. [ECOS 개발 명세](https://ecos.bok.or.kr/api/#/DevGuide/DevSpeciflcation)(오류 코드 INFO-100·INFO-200·ERROR-301 등). 서울외국환중개는 매매기준율과 재정된 매매기준율을 "은행 영업일(월~금) 1회(9시 이전)" 고시한다([서울외국환중개 매매기준율](http://www.smbs.biz/ExRate/StdExRate.jsp)). ECOS에는 13:50 KST에 이미 당일 값이 있었다. ADR-0001이 인용한 한국은행 스냅숏의 원/엔은 하나은행 15:30 기준으로 다른 계열이라 쓰지 않는다.
- **서버가 받고, 원문을 검사한다.** 서버는 ECOS 응답 원문(JSON)을 그대로 받아(`ingest_ecos_jpy_rates`, service_role 전용) 직접 검사한다. 통계표·항목·항목 이름·단위가 위와 같아야 한다. 날짜는 요청 기간 안의 실제 날짜여야 하고 같은 날짜가 두 번 오면 안 된다. 값은 소수 넷째 자리까지의 양수 글자여야 하고(부동소수·쉼표·지수 표기 거절), 전체 건수가 받은 줄 수와 같아야 한다(잘린 쪽 거절). 데이터 없음(INFO-200)만 빈 결과로 받고 나머지 ECOS 오류는 거절한다. 기간은 KST로 이미 끝난 날까지만 받는다(오늘·미래 날짜 거절). 하나라도 어긋나면 아무것도 넣지 않는다. 받기 기록(`fx_ingestions`: 기간·받은 시각·응답 해시·출처 종류)과 고시값(`fx_quotes`)은 바꾸거나 지울 수 없다(트리거). 앱 역할은 두 표를 읽지 못하고 장부·검토 RPC가 필요한 값만 돌려준다.
- **지출일 기준(as-of).** 지출일 D에서 하루씩 거슬러 간다. 그날을 덮는 가장 최근 받기 기록에 고시값이 있으면 그 값을 쓴다. 지출일에 고시가 없으면 그 전 가장 최근 고시일 값이 되고, 화면에 그 사실을 적는다. 그날을 덮는 받기 기록이 없으면 "아직 확인 못 함"(`undetermined`)이다. 그날 고시가 있었는지 모르므로 앞날 값으로 넘어가지 않는다. 31일 안에 값이 없으면 "쓸 수 없음"(`unavailable`)이다. 지출일 뒤에 고시한 값은 쓰지 않는다. 같은 날짜를 다시 받으면 새 받기 기록이 이긴다(정정). 정하기 함수는 시각 인자를 받아 그때까지 받은 기록만으로 다시 정할 수 있다.
- **정확한 계산, 지출마다 원 단위 반올림.** 예상액은 엔 × 고시값 ÷ 100, 취득 원가는 엔 × 환전에 쓴 원화 ÷ 받은 엔이다. 정확한 십진·정수 계산(`div(2n + d, 2d)`) 뒤 원 단위로 반올림하고 양수 .5는 올린다. 0원이 되거나 1,000억 원 이상이면 쓸 수 없다. 몫은 그 원화로 나눈다. 두 사람 홀수 금액은 [ADR-0007](0007-two-person-even-split.md)대로 결제자가 1원을 더 부담한다. 행의 검사 제약도 같은 함수로 원화를 다시 계산해 맞는지 본다. 두 앱과 서버는 공통 예제(`apps/fixtures/settlement/examples.json`의 `krw_conversions`)로 같은 답을 내는지 본다. 앱은 서버가 준 예상액을 고시값으로 따로 다시 계산해 같을 때만 쓴다.
- **본 고시값으로만 승인한다.** 예상액 승인에는 방장이 본 고시값(`p_fx_quote_id`)과 원화가 함께 간다. 그사이 그 지출일의 제안이 바뀌었으면(정정, 늦게 들어온 고시) `stale_quote`(409)로 거절한다. 앱은 고른 기준을 그대로 두고 새 제안을 불러와 다시 저장하게 한다(새 요청 키). 값이 같은 다시 받기는 그대로 받는다. 원화가 서버 계산과 다르면 `krw_mismatch`다. 포함하면 고시값·기준일·단위와 원화를 지출에 고정한다. 나중에 들어온 고시값은 포함한 금액·미리보기·확정을 바꾸지 않는다. 장부에 `fx_superseded`로만 알리고, 방장은 다시 검토할 수 있다. (확정 차단과 유지 결정은 [ADR-0009](0009-fx-correction-before-finalize.md)가 대신한다.)
- **외화 취득 원가는 방장이 적은 두 숫자다.** 환전에 쓴 원화와 받은 엔이다. 지출마다 적는다. 출금·환전 증빙 파일이나 은행 기록은 받지 않고, 출처 표시는 고정 문구("증빙으로 확인한 환전 원가")다. 수수료는 적은 원화에 포함된 만큼만 반영한다(ADR-0001). 엔화만 받는다.
- **확정 스냅숏 v2.** 새 확정본은 `explicit-krw-shares-v2`다. v1에 지출마다 원화 기준과 근거(고정한 고시값의 출처·통계표·항목·단위·고시값·기준일·받은 시각·출처 종류, 또는 취득 원가 두 숫자)와 `is_estimate`, 결과의 `estimated_total_krw`(함께 쓴 돈 가운데 예상액)를 더했다. 그때의 제안(`fx_proposal`)은 넣지 않는다. 이미 확정한 v1 행은 바뀌지 않는다. 앞 마이그레이션에서 만든 v1 확정본과 검토 요청을 새 마이그레이션 뒤에 다시 읽어 확인했다(`mise run local:fx-upgrade`). 스냅숏 입력만으로 기준별 원화·합계·잔액·송금을 다시 계산하면 같은 결과가 나온다(`mise run local:fx-contract`).
- **표시는 고정 문구, 실패하면 닫힌다.** 예상액은 장부·검토·송금표·확정본에서 언제나 "예상 금액"과 "한국은행 ECOS 원/일본엔(100엔) · 기준일 고시 · 100엔당 고시값원"으로 보인다. 가상 시험값은 "가상 시험 환율 · 시장 환율 아님"으로 따로 표시한다. 송금표에는 "이 중 예상 금액(기준환율)"과 "원화 환산 근거" 목록이 있다. 앱은 모르는 기준, 근거 없는 예상액·취득 원가, 기준과 다른 예상 표시, 다른 시리즈·단위의 고시값, 글자가 아닌 고시값, 지출일 뒤 고시일, 모르는 규칙 판, 예상액이 든 v1 확정본을 받으면 그리지 않는다(`.unknown`).
- **키와 가상 시험값.** ECOS 키는 환경 변수 `ECOS_API_KEY`로만 받는다. 1Password `nonanona` vault 항목을 `.env.tpl`에 적고 `op run`으로 주입한다. 항목은 아직 없고 그 줄은 주석이다. 키가 요청 URL 경로에 들어가므로 URL·키·응답 원문은 출력하지 않는다. 새 키·계정은 만들지 않았다. 로컬 개발과 시험은 가상 시험값(`supabase/fixtures/fx-jpy-synthetic.json`, 실제 고시값과 일부러 다른 숫자)을 DB 소유자 권한으로만 넣는다(`data_origin = fixture`). API(service_role) 길은 언제나 `ecos_live`로 기록한다.

## 하지 않은 것

- 엔화 밖의 통화, 여러 환전에서 마련한 현금을 섞어 쓴 경우, 취득 원가를 여러 지출에 한 번에 적용하기, 확정 후 정정, 영수증 공유 정책 변경, 수수료를 따로 다루기.
- 정기 받기(스케줄러), 배포, 클라우드 프로젝트, 별도 서버 앱, 앱 안의 키. 받기는 사람이 `mise run fx:ingest`로 돌린다.

## 대가

- 당일 지출은 다음 날 받기 전까지 예상액이 없다. ECOS에는 9시 전 고시 뒤 당일 값이 있지만, 그날 안에 값이 바뀌지 않는다고 확인하지 않아 끝난 날만 받는다.
- 31일은 거슬러 찾는 한도다. 31일 넘게 고시가 없는 계열은 예상액을 만들지 않는다.
- ECOS가 항목 이름·단위를 바꾸면 받기가 거절된다. 사람이 확인하고 마이그레이션을 고쳐야 한다(`mise run fx:series`).
- `ecos_live`라는 표시는 service_role 키를 가진 호출자를 믿는다. 서버는 응답이 정말 ECOS에서 왔는지 증명하지 못한다.
- 한 DB에 가상 시험값과 실제 값이 섞일 수 있다(로컬에서 `fx:ingest`를 돌린 경우). 고시값마다 출처 종류를 표시하고 날짜별로 새 받기 기록이 이긴다.
- 이 마이그레이션 전의 앱은 예상액을 "예상" 없이 그린다. 배포한 앱이 없어 지금은 문제가 아니다.
