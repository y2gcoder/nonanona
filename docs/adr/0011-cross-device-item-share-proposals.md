# 다른 기기에서 올린 영수증의 품목 나누기: 올린 사람이 "제안 몫"만 보내고 방장이 확인한다

상태: accepted (2026-11-24, 로컬 슬라이스). [ADR-0010](0010-on-device-item-split.md)의 "정하지 않은 것" 중 "다른 기기에서 올린 영수증의 품목을 방장이 볼 수 있게 할지"를 선택지 (a)로 정한다. 같은 기기 방장 흐름(ADR-0010)은 그대로다. 서버는 `supabase/migrations/20261124170000_item_share_proposals.sql`, 앱은 두 앱의 `Features/Settlement/ShareProposal.swift`·`feature/settlement/ShareProposal.kt`와 품목 나누기 화면의 제안 모드다.

사용자가 (a)를 승인했다. 회원이 올린 영수증(대부분)은 품목 글자가 회원 기기에만 있어 방장이 품목으로 나눌 수 없었다. 품목 글자를 여행방에 올리지 않고(ADR-0003·0005·0010의 경계 그대로) 올린 사람이 자기 기기에서 계산한 사람마다 원 단위 몫만 따로 동의를 받아 보낸다. 방장은 그 몫을 보고 확인한 뒤 기존 검토로 포함한다.

## 결정

- **보내는 값은 이것뿐이다.** 지출 ID, 올린 사람이 본 지출 버전, 요청 키, 원화 기준과 그 원화 합계, (기준환율 예상액이면) 본 고시값 ID, 사람마다 {구성원 ID, 원}. RPC `propose_expense_shares`의 서명에 다른 필드가 없고, 몫 한 줄은 정확히 `user_id`·`krw` 두 키여야 한다(이름 등이 붙으면 `shares_invalid`). 앱의 보내는 타입(`ShareProposalRequest`)에도 품목 이름·품목 금액·OCR 줄·조정 줄·사진이 들어갈 자리가 없다. 이미 승인한 가린 사본 올리기 경로는 바꾸지 않았다.
- **누가.** 그 지출을 실제로 올린 구성원만(`uploaded_by` = 나, 사본으로 올린 지출). 다른 구성원은 `uploader_only`(403), 비구성원·없는 지출은 지금처럼 `trip_not_found`(404)로 구분하지 않는다. 앱은 회원 기기에서, 장부의 내 지출이 이 기기에서 확인한 영수증(사본 해시·확인한 값이 같음, ADR-0010)일 때만 "품목으로 나눠 방장에게 제안"을 보인다. 방장 기기는 지금처럼 직접 나눈다. 서버는 방장이 올린 지출이면 방장도 받는다(다른 기기에서 올린 방장).
- **방장이 볼 수 있고 승인할 수 있는 원화에만 묶는다.** 
  - KRW 지출: 원래 금액(`krw_original`).
  - 엔화 지출: 방장이 이미 실제 청구액·환전 원가로 포함했으면 그 원화(`verified_krw_charge`·`acquisition_cost`, 올린 사람이 바꾸지 못한다). 아니면 지금 그 지출일에 적용되는 기준환율 예상액(`reference_rate_estimate`, 본 고시값 ID). 서버는 고시값의 실질 식별(ADR-0009 `fx_identity`)이 지금 적용 값과 같고 합계가 그 예상액일 때만 받는다(`stale_quote`·`krw_mismatch`).
  - 그 밖(엔화인데 고시값 없음·확인 못 함이고 방장이 원화를 정하지 않음, 다른 외화)은 제안하지 않는다. 앱은 "원화 기준이 없어 제안할 수 없어요"를 보인다. 실제 청구액을 올린 사람이 적게 하는 길은 만들지 않았다(방장이 확인하는 값이라서).
- **몫은 정확하고 저절로 정하지 않는다.** 양의 정수 원, 구성원만, 한 사람 한 줄, 합 = 원화 합계. 품목 계산(ADR-0010의 정확한 분수)이 나눠떨어지지 않으면 올린 사람이 남은 원을 낼 사람(그 영수증에 몫이 있는 사람)을 직접 고를 때까지 보내지 않는다. 결제자는 아직 정해지지 않았으므로 ADR-0007의 결제자 +1원도 쓰지 않는다. 고른 사람은 그때의 원화 합계에 묶여, 기준이 바뀌면(정정 등) 다시 고른다. 세금·할인은 ADR-0010처럼 조정 줄로 사용자가 정한다.
- **보내기 전에 따로 동의한다.** "방장에게 제안 보내기"를 누르면 보낼 값(사람마다 원, 합계, 원화 기준)과 "품목 이름·품목 금액·영수증 글자는 보내지 않아요"를 보이는 확인 창이 뜨고, "보내기"를 눌러야 간다. 창을 연 뒤 값이 바뀌었으면 보내지 않는다.
- **적용하지 않는다.** 제안은 장부 몫(`expense_shares`)·지출 상태·방 revision·확정 계산과 스냅숏(v2)을 바꾸지 않는다. 방장은 검토 화면의 "올린 사람의 품목 나누기 제안"에서 기준·합계, 사람마다 제안 몫과 지금 입력(또는 포함한) 몫, 상태를 본다. "제안 몫을 직접 나누기에 채우기"는 입력만 바꾸고(엔화 예상액이면 원화 기준을 기준환율 예상으로) 보내지 않는다. 결제자를 고르고 "포함하기"를 눌러야 기존 `review_expense`로 들어간다. 지금 제안이 아니거나 방장이 고를 수 있는 원화와 다르면 채울 수 없다. 받지 않은 제안이 있어도 확정을 막지 않는다.
- **보이는 사람.** 올린 사람과 지금 방장만. 제안 표는 앱 역할이 읽지 못하고(권한·정책 없음), 장부가 그 두 사람에게만 지출마다 가장 최근 제안을 준다(`share_proposal`). 다른 구성원의 장부에는 null이다.
- **상태와 오래된 제안.** 장부의 상태: `current`(그 버전·기준 그대로), `stale_expense`(그 뒤 다시 검토됨), `stale_basis`(고시값 정정 등), `applied`(포함한 원화·몫이 제안과 같음), `closed`(확정된 방에서 쓰이지 않음). 같은 값의 다시 받기는 정정이 아니다(ADR-0009와 같은 비교). 오래된 제안은 고쳐 쓰지 않고, 올린 사람이 새 값으로 다시 보낸다.
- **잠금·재시도.** 여행방 잠금 → 지출 잠금 → (예상액이면) 기준환율 공유 잠금. 방장 검토와 같은 잠금으로 직렬화되어 늦게 온 제안은 `stale_expense`다. 요청 키는 앱이 내용(지출·버전·기준·합계·고시값·몫, 순서 무관)으로 정한다(두 앱 같은 값). 같은 키·같은 내용은 같은 제안(`replayed`, 확정 뒤에도), 같은 키의 다른 내용·다른 계정은 `idempotency_conflict`. 제안 행은 바꾸거나 지울 수 없다. 새 제안은 새 행이고 장부는 가장 최근 것을 보인다. 확정 뒤 새 제안은 `trip_finalized`.
- **예전 앱·읽기.** 장부 응답에 키 하나가 더해질 뿐이라 예전 앱은 무시한다. 새 앱은 제안 해석을 실패 시 닫는다(모르는 상태·기준, 합 불일치, 0원·중복·구성원 아닌 몫, 올린 사람이 아닌 제안자, 기준과 고시값 짝 불일치, 지출보다 새 버전 → 장부 전체 `.unknown`).

## 확인

- 서버 계약 시험 `mise run local:share-proposal-contract`(78개): 권한(올린 사람·다른 회원·바깥 계정·방장이 올린 지출), 몫 형식, 기준 묶기와 정정 뒤 stale, 같은 값 다시 받기, 재시도·키 충돌, 방장 검토와 잠금 경쟁, 동시 제안 둘, 보이는 사람·표 직접 읽기 거절, 표에 품목 글자 열 없음, 행 불변, 확정에 닿지 않음·확정 뒤 거절·재시도 수렴. 기존 계약 시험(정산 100, 엔화 114, 정정 71)도 그대로 통과.
- 두 앱 단위 시험: 실제 서버 응답(가상 값, `apps/fixtures/settlement/proposal-responses`) 해석과 실패 시 닫힘, 보내는 본문의 키, 공통 요청 키 벡터, 기준 묶기, 남은 원의 명시적 선택, 방장 채우기·비교, typed 실패.
- 두 기기 E2E `mise run e2e:proposals`를 역할을 바꿔 두 번 통과했다(iOS 시뮬레이터 올린 회원 → Android 에뮬레이터 방장, Android 올린 회원 → iOS 방장, 2026-11-24). 올린 회원이 i01(3,500엔, 가상 시험 환율 902.15 → 31,575원)을 품목으로 나누면 1원이 남아 고르기 전에는 보낼 수 없고, 가나에게 주고 동의하면 다라 20,005·가나 11,570원 제안 1건(같은 내용 두 번 → 같은 요청 키·행 1개, 방 revision 그대로). 그 지출일 환율을 903.15로 정정하면 방장 화면은 "원화 기준이 바뀌어 쓸 수 없어요"(채우기 없음), 올린 회원 장부도 stale. 다시 열면 남은 원 선택이 지워져 있고 다라에게 주어 31,610원(20,028·11,582)으로 다시 보낸다. 방장이 제안 몫·입력 몫을 보고 채우고 결제자를 골라 포함 → 서버 몫 = 제안, 상태 applied. 확정본 합계 31,610원·잔액 합 0·송금 11,582원, 스냅숏에 제안 없음, 확정 뒤 제안 `trip_finalized`, 올린 회원 화면에 제안 단추 없음. 두 앱이 기록 프록시로 오간 REST/RPC 본문 전체(로그인 본문·헤더 제외, 두 앱 모두 확인)와 서버 DB 전체(pg_dump)에 품목 글자·계획 키가 없고, 제안 요청 본문은 허용한 키뿐이다. 화면: `docs/design/screens/*proposal*`.
- E2E가 찾은 버그를 고쳤다: iOS 확인 창은 "보내기" 동작보다 먼저 닫히며 확인 대상을 지워 보내기가 조용히 무시됐다(대상과 요청을 버튼에 그대로 넘긴다. Android도 같은 모양으로 바꿨다). 방장 비교는 결제자를 고르기 전에도 입력한 몫과 비교한다.

## 대가와 남은 것

- 올린 사람이 보낸 몫을 방장이 품목 단위로 검증할 수 없다. 방장은 합계·사람마다 금액만 보고 받거나 직접 고친다(품목 글자를 보내지 않는 대가).
- 엔화 지출에 실제 청구액이 따로 있을 때는 방장이 먼저 그 원화로 포함해야 올린 사람이 그 원화로 제안할 수 있다(포함 → 제안 → 다시 포함). 기준환율 예상액으로 제안한 뒤 방장이 실제 청구액으로 포함하면 지출 버전이 올라 제안은 `stale_expense`가 되고, 올린 사람이 그 원화로 다시 보내야 한다.
- 제안은 결제자를 모른다. 두 사람 몫이 똑같고 원화가 홀수여도 ADR-0007(결제자 +1원)을 쓰지 않고 올린 사람이 고른다. 방장은 채운 뒤 직접 고칠 수 있다.
- 방장 기기에서 올린 영수증은 지금처럼 같은 기기에서 직접 나눈다(제안 화면을 보이지 않는다). 방장이 다른 기기로 올린 경우의 앱 진입점은 없다(서버는 받는다).
- 제안 기록(`expense_share_proposals`)은 확정본에 들어가지 않고 서버 표에만 남는다. 지우는 정책은 없다.
