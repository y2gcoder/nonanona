# 여행방 정산: 서버가 확정하고, 몫은 원 단위로 방장이 정한다

상태: accepted (2026-11-24, 로컬 슬라이스). "남는 원을 누구에게 줄지 정하지 않는다"의 두 사람 반씩 부분은 superseded by [ADR-0007](0007-two-person-even-split.md)(홀수 금액은 결제자가 두 사람 중 한 명이면 결제자가 1원을 더 부담한다). "원화는 확정된 값만 받는다 … 기준환율 자동 환산은 없다"의 엔화 부분은 superseded by [ADR-0008](0008-jpy-reference-rate.md)(엔화는 실제 청구액 → 외화 취득 원가 → 한국은행 기준환율 예상 순으로 방장이 고르고, 예상액은 "예상"으로 표시한다).

여행방 구성원은 같은 지출을 보고, 방장이 지출마다 결제자·원화·부담 몫을 정해 포함하거나 보류한 뒤, 서버가 계산한 송금표를 확정한다. [원화 환산 기준](0001-krw-conversion.md)의 기준환율 제공처와 원 단위 반올림·잔여 원 배분, 확정 후 정정 방식이 아직 정해지지 않았으므로, 이번 슬라이스는 그 규칙을 고르지 않는 쪽으로 만들었다. 서버 쪽은 `supabase/migrations/20261124090000_room_settlement.sql`, 앱 쪽은 두 앱의 `Features/Settlement`(iOS)·`feature/settlement`(Android)다.

## 결정

- **서버가 계산하고 확정한다.** 미리보기와 확정은 같은 서버 함수(`compute_settlement`)로 계산하고, 앱은 서버 값을 그리기만 한다([ADR-0003](0003-mobile-architecture.md)). 앱이 하는 계산은 두 사람 반씩 몫([ADR-0007](0007-two-person-even-split.md))뿐이고, 공통 예제(`apps/fixtures/settlement/examples.json`)로 두 앱과 서버 계약 시험이 같은 답을 내는지 본다.
- **역할을 따로 둔다.** 올린 사람(`uploaded_by`), 결제자(`payer_id`), 부담 몫(`expense_shares`, 사람마다 원 단위 정수). 구성원이 올린 지출은 언제나 "확인 필요"로 들어오고, 결제자와 몫은 방장이 검토에서 정한다.
- **원화는 확정된 값만 받는다.** (엔화는 [ADR-0008](0008-jpy-reference-rate.md)이 대신한다. 다른 외화는 그대로다.) KRW 지출은 원래 금액, 외화 지출은 방장이 확인한 실제 원화 청구액만 받는다(`krw_basis` = `krw_original` | `verified_krw_charge`). 기준환율 자동 환산은 없다. 원화를 모르면 확인 필요로 두거나 사유와 함께 보류한다. 그래서 ADR-0001의 우선순위 2·3(외화 취득 원가, 기준환율 예상액)은 이번에 쓰지 않는다.
- **몫은 정확히 맞아야 한다.** 서버는 몫의 합이 원화와 같을 때만 포함한다(`shares_mismatch`). 앱은 "한 사람", "둘이 반씩", "직접 나누기"를 제공한다. ~~13,377원처럼 반으로 나누면 1원이 남으면 반씩을 막고 직접 나누게 한다. 남는 원을 누구에게 줄지 서버·앱이 정하지 않는다.~~ 두 사람 반씩의 홀수 금액은 [ADR-0007](0007-two-person-even-split.md)을 따른다(13,377원이면 결제자 6,689원·다른 사람 6,688원). 결제자가 두 사람 밖이면 지금처럼 직접 나눈다. 서버는 여전히 남는 원을 정하지 않고 받은 몫만 검사한다.
- **몫은 줄 단위로 저장한다.** 지출 행에 비율을 두지 않고 몫 줄(지출, 사람, 원)로 둔다. 품목별·묶음별 나누기는 몫 줄에 묶음 열을 더하고, 사람별 몫은 묶음 몫의 합으로 넓힐 수 있다(이번에는 묶음이 하나).
- **모든 쓰기가 같은 잠금과 revision을 거친다.** 쓰기 RPC(지출 제출·직접 입력·검토·가입·확정)는 여행방 행을 잠그고 `revision`을 올리며 `trip_events`에 남긴다. 검토는 지출 `version`, 확정은 방장이 본 `revision`으로만 한다. 늦은 쪽은 덮어쓰지 않고 `stale_expense`·`stale_revision`으로 거절되며, 앱은 최신 값을 다시 불러와 보인다.
- **재시도는 같은 결과다.** 지출 제출은 (여행방, 요청 키) 고유 키와 요청 지문, 검토는 `settlement_requests`, 확정은 `finalizations`의 (여행방, 요청 키). 같은 요청은 같은 결과(`replayed`), 같은 키의 다른 내용은 `idempotency_conflict`. 앱은 응답을 못 받은 같은 검토·확정을 다시 보낼 때 같은 키를 쓴다.
- **확정은 입력과 결과를 함께 고정한다.** 확인 필요 지출이 없어야 확정할 수 있다(`pending_review`). 확정 순간의 구성원·지출(원래 금액·통화·원화·기준·몫·종류)과 잔액·송금·제외 목록을 스냅숏(SHA-256 포함)으로 남기고 방을 `finalized`로 잠근다. 확정 행은 테이블 소유자도 바꿀 수 없다(트리거). 보류 지출과 개인 지출(결제자 혼자 전부 부담)은 송금에서 빠지고 제외 목록에 사유와 함께 남는다. 기기는 다시 계산하지 않고 이 스냅숏을 그린다.
- **증빙 없는 직접 입력은 따로 동의받고 올린다.** 읽지 못한 사진에 값만 확인한 항목(ADR-0005의 `confirmManual`)은 기기 경계(`outboundManualEntries`)를 지난 허용 필드(날짜·금액·통화·가게)만 `submit_manual_expense`로 보낸다. 사본 올리기와 같은 최종 확인 창을 따로 띄우고, 동의한 항목과 보낼 항목이 다르면 보내지 않는다. 요청 키는 (여행방, 초안, 사진)이다. 빈 이미지·흐린 원본·OCR 전문은 보내지 않는다. 사진이 전혀 없는 지출을 여행방 화면에서 새로 적는 입력은 아직 없다.
- **확정 뒤에는 아무것도 바뀌지 않는다.** 새 지출·직접 입력·검토·재확정과 확정된 방에 처음 참여하는 초대 수락은 `trip_finalized`로 거절한다(여행방 잠금 뒤, 어떤 쓰기보다 먼저). 이미 올린 요청과 그 초대로 이미 참여한 계정의 재시도는 기존 결과로 수렴한다. 앱은 확정된 방 초대를 만료·쓸 수 없는 초대처럼 지우고 다시 시도 버튼 없이 알린다. 정정 흐름은 없다.
- **검토 입력은 연 버전에 묶는다.** 앱의 검토 입력은 연 지출 버전을 들고 있다가 그 버전으로 보낸다. 장부를 새로 읽었을 때(입력 중 도착한 새로고침 포함) 버전이 바뀌었으면 입력을 최신 값으로 다시 채우고 알린다. 옛 버전에서 만든 몫을 새 버전에 덮어쓰지 않기 위해서다.

- **방장은 검토 화면에서 공유한 가림 사본만 본다.** 장부가 지출마다 사본의 경로·해시를 알려 주고(구성원은 이미 RLS로 읽을 수 있던 값), 앱은 비공개 버킷 `receipts`를 인증 다운로드로 받는다(구성원만 읽는 기존 정책, 공개·서명 URL 없음). 보내기 전에 경로가 지금 여행방의 사본 경로인지, 받은 뒤 PNG이고 장부의 해시와 같은지 확인해 같은 바이트만 보인다. 받은 사본은 메모리에만 두고(디스크·HTTP 캐시 없음) 검토 화면을 떠나거나 세션·여행방이 바뀌면 지운다. 해시가 맞아도 PNG 구조가 온전하고 플랫폼 디코더가 그림을 만들 때만 보인다. 사본은 지금 계정과 연 여행방 맥락에서만 받고, 응답이 올 때 그 맥락이 그대로일 때만 보인다. Storage의 `AccessDenied`는 Auth로 토큰을 확인해 진짜 거절과 토큰 문제를 가르고, 토큰 문제는 한 번만 갱신해 다시 받는다. 실패(권한·없음·연결·해시 다름·그림으로 풀리지 않음·세션 만료)는 다시 시도할 수 있고 검토를 막지 않는다. 직접 입력은 "증빙 없음"이다. 원본 사진과 OCR 글자는 처음부터 기기를 떠나지 않으므로([ADR-0003](0003-mobile-architecture.md), [ADR-0005](0005-receipt-review-and-mask-correction.md)) 서버에도, 이 화면에도 없다. 대가: 저장소는 없는 사본과 구성원이 아니라 읽을 수 없는 사본을 같은 응답(NoSuchKey)으로 알려 앱이 둘을 구분하지 못하고, 토큰 문제를 가르려고 Auth에 한 번 더 묻는다.

## 아직 정하지 않은 것 (제품 결정)

- 확정 후 정정(새 확정 판을 여는지, 방을 새로 만드는지 — 협업 초안 D1)과 송금 완료 체크.
- 기준환율 제공처·미공표일·환산의 원 단위 반올림(ADR-0001 미정). 엔화는 [ADR-0008](0008-jpy-reference-rate.md)에서 정하고 "예상 금액"을 더했다. 다른 통화는 아직이다. 잔여 원 배분은 두 사람 반씩만 정했다([ADR-0007](0007-two-person-even-split.md)). 결제자가 두 사람 밖인 홀수 금액과 세 명 이상 나누기는 아직 정하지 않았다.
- 품목별 나누기 화면: 품목 줄(이름·가격)은 OCR 전문에서 나오고 지금은 기기 밖으로 나가지 않는다(협업 초안 D3). 품목을 여행방에 올릴지, 기기에서만 몫 계산에 쓰고 결과 몫만 올릴지가 정해져야 화면을 만들 수 있다.
- 구성원이 자기 지출을 고치거나 지울 수 있는지(지금은 방장만 검토한다), 세 명 이상에서 "반씩"을 어떻게 보일지.
