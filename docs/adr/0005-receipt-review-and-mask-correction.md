# 영수증 검토와 가림 고치기

상태: accepted (2026-11-23). "읽지 못한 사진의 직접 입력은 값만 기기에 남긴다"의 올리지 않는 부분은 superseded by [ADR-0006](0006-room-settlement.md)(직접 입력은 따로 최종 확인을 받고 허용 필드만 올린다). "현재 Android 구현"의 한국어 OCR 미포함과 "현재 iOS 구현"의 한국어 인식 확인 조건은 superseded by [ADR-0013](0013-android-korean-ocr.md).

영수증 10장을 받은 뒤 사용자는 목록에서 상태를 먼저 보고, 한 장씩 원본과 비교해 값과 가림을 확인한다(QA 권고: A의 목록을 첫 화면으로, B의 "확인하고 다음"을 연속 검토 경로로). 확인한 것만 기기 밖으로 나갈 수 있으므로([ADR-0003](0003-mobile-architecture.md)), 검토 화면의 결정은 무엇이 여행방에 올라가는지를 정한다.

## 결정

- **가림 고치기는 줄 켜기와 가로 띠다.** OCR이 찾은 줄은 줄마다 스위치(글자 크기를 따라 커지는 목록 행)로 가리거나 푼다. OCR이 줄을 찾지 못한 곳은 "가림 영역 더하기"로 가로 전체 띠를 더하고, 버튼(위로·아래로·넓게·좁게·삭제)과 화면 읽기 조절 동작으로 옮긴다. 위치는 사진 높이의 정수 퍼센트(이동 2%, 크기 1%)라 두 플랫폼이 같은 픽셀을 굽는다. 손가락으로 사각형을 그리는 방식은 화면 읽기·큰 글자·운동 제약 사용자가 쓸 수 없어 고르지 않았다. 대가: 띠는 같은 높이의 다른 정보도 덮고, 2% 단위보다 세밀하게 맞출 수 없다.
- **미리보기는 확인과 같은 굽기 함수다.** "가린 사본"은 확인 때 만들 PNG를 그대로 보여 주고 디스크에 쓰지 않는다. 화면 읽기에는 "가린 사본 미리보기, 가림 N곳"만 읽히고 가린 글자는 읽히지 않는다. 원본 보기의 OCR 줄 글자는 기기 안 검토에만 보인다.
- **읽지 못한 사진의 직접 입력은 값만 기기에 남긴다.** 사본 없이 확인(`confirmManual`)하고, 이번 단계에서는 올리지 않는다. 지금 서버(`submit_receipt_expense`)는 사본이 있는 지출만 받고, 흐린 원본을 사본으로 대신 보내지 않기 위해서다. 올리기 화면은 "직접 입력 N건은 이번에는 올리지 않아요"를 보인다. 사진 없는 지출을 서버에 넣는 일은 정산 단계에서 결정한다.
- **확인은 "확인하고 다음" 한 가지다.** 누르면 그 사진을 확인해 디스크에 쓰고(가린 사본 또는 직접 입력), 목록 순서(사진 번호)로 다음 "확인 필요" 사진을 연다. 뒤에 없으면 앞쪽, 그것도 없으면 목록으로 돌아가 남은 것(읽지 못함·읽는 중)을 보인다. 건너뛰기·나중에 버튼은 없다. 검토 화면을 나가도 확인되지 않는다. 확인한 사진은 고칠 수 없다(같은 사본으로 이미 올렸을 수 있어, 다시 만들면 다른 요청 키의 지출이 생긴다).
- **고치던 입력은 사진마다 디스크에 둔다.** 초안 폴더 `reviews/<사진>.json`(값 글자 그대로, 가릴 줄, 띠)에 고칠 때마다 원자적으로 쓰고 확인하면 지운다. 값이 비어 있으면 OCR 제안을 쓴다. 그래서 앱 종료, 창 배치 변경, 그 사진만 다시 읽기를 지나도 입력이 남는다.
- **검토 화면은 목록·상세의 상세 쪽에 붙인다**([ADR-0004](0004-adaptive-layout.md)). iOS는 분할 보기 상세 열 안의 쌓기(초안 위에 검토), Android는 세 번째 칸(`extraPane`, 두 칸이면 영수증 목록 옆)이다. 검토 화면 자체는 한 열로만 쌓아 접힘 피하기를 시스템 컨테이너에 맡긴다. 고른 영수증은 안정 ID(초안 ID + 사진 ID)로 모델에 둔다.
- **release에서도 검토·확인을 할 수 있다.** 올리기와 개발용 바로 확인 버튼만 debug 전용이다.

## 리뷰 뒤 보강 (2026-11-23)

008d3c3 독립 리뷰의 차단 항목을 반영했다. 위 결정은 그대로이고 다음을 더한다.

- **확인은 디스크에 남은 뒤에만 보인다.** 처리기는 확인(`confirm`, `confirmManual`)한 처리 상태(`processing.json`)를 먼저 쓰고, 쓰기에 성공했을 때만 메모리 상태를 바꾸고 화면에 알린다. 실패하면 만든 사본을 지우고 확인 전 상태와 검토 입력을 그대로 둔 채 오류를 던진다. 앱은 그때 다음 사진으로 가지 않고 "확인을 저장하지 못했어요…"를 보인다. 검토 입력 파일은 확인이 디스크에 남은 뒤에만 지운다.
- **입력 저장 실패를 숨기지 않는다.** 고친 입력을 쓰지 못하면 "입력을 기기에 저장하지 못했어요"와 "다시 저장"을 보이고, 화면·메모리의 입력은 그대로 둔다. 디스크에는 마지막으로 쓴 입력이 남는다(앱을 다시 열면 그 값). 저장에는 순번을 붙여, 늦게 도착한 오래된 입력이 새 입력을 덮지 않는다.
- **최종 확인은 동의한 내용 그대로만 보낸다.** 확인 창을 열 때 기기 경계를 지난 영수증을 사진 ID·사본 해시·확인한 값(날짜·금액·통화·가게)으로 적어 두고, 여행방 ID와 함께 보관한다. 보내기 직전 다시 경계를 지난 목록이 하나라도 다르면(장수, 사진, 사본, 값) 아무것도 보내지 않고 "올릴 영수증이 바뀌어 아무것도 올리지 않았어요"를 보인다.
- **날짜·금액 입력은 일부러 ASCII로 맞춘다.** 모든 유니코드 10진 숫자(전각, 아랍-인도 등)를 0–9로, 줄표·빗금·마침표 변형을 구분자로 바꾼 뒤 ASCII 형식만 받는다. 날짜는 숫자 8자리(`20261108`), `2026/11/8`도 받아 `2026-11-08`로 저장한다(Android 숫자 자판에서 구분자 없이 칠 수 있게). 세 부분을 숫자로 모두 읽은 뒤에만 쓴다.
- **Android 사진 디코딩은 하나다.** OCR, 가림 굽기, 검토 화면 원본·가림 표시, 목록 미리보기가 같은 함수(EXIF 방향 8가지 적용)를 쓴다. 예전에는 화면만 방향을 무시해 EXIF가 붙은 사진에서 원본 그림과 가림 표시가 어긋날 수 있었다. iOS는 처음부터 모두 방향을 적용한 같은 디코딩(ImageIO 변환)이다.

## 가림 보강 1단계 (2026-11-26)

이슈 #8에서 기울기·흐림·번짐으로 민감 번호가 사본에 남는 경우를 확인했다. 줄 스위치, 수동 가로 띠, 같은 굽기 함수를 쓰는 미리보기와 사본, “확인하고 다음”을 유지한다.

- **자동 가림 범위**는 카드·회원·승인·예약 번호와 가게 전화(TEL)다. 가게명·주소·레지 ID·사업자 등록번호는 보존한다. 민감 라벨과 같은 행·바로 다음 행의 번호 조각, 라벨 없이도 식별 가능한 카드 표기와 긴 숫자열을 후보로 찾는다. 일본어·한국어·영문 라벨과 OCR 오독을 판정에 반영한다.
- **가격과 날짜는 해당 범위만 보존한다.** 민감 번호와 가격·날짜가 한 OCR 상자에 묶이면 가능한 경우 번호의 글자 범위를 덮는다. 위치를 분리할 수 없으면 줄 전체를 덮고 확인을 안내한다.
- **불확실성을 알린다.** 짝 없는 민감 라벨, 위치를 분리할 수 없는 혼합 줄, 행별 기울기 차이, 글자 영역의 흐림·저대비, 사본 재OCR에서 남은 민감 정보가 안내 조건이다. 가린 사본에서는 보호 규칙과 분리해 원래 라벨·번호의 부분 문자열 및 가림 행 주변의 번호를 확인하는 것이 목표다. Ready 상태에서 “가림이 충분한지 확실하지 않아요. 번호가 보이지 않는지 확인해 주세요.”를 보인다. 사용자 보기를 기억하되 안내가 있는 사진을 열면 사본을 먼저 보인다. 안내로 확인을 막지 않는다.
- **원본과 재OCR은 기기 안에 둔다.** 긴 사진은 겹치는 타일로 읽는다. 처리에 새 권한·네트워크 경로·의존성을 추가하지 않는다. 각 플랫폼의 가림 외곽, 품질 지표, 타일 크기는 같은 픽셀·안내 목표를 기준으로 각각 검증한다.

### 현재 Android 구현

- ML Kit 번들 일본어·라틴 문자를 사용한다. 한국어 라벨 문자열 판정은 있지만 한국어 OCR 모델을 포함하지 않는다. 한국어 합계만 있는 가상 입력에서는 제안 사본을 만들지 못했다. (superseded by [ADR-0013](0013-android-korean-ocr.md): 번들 한국어 모델을 함께 쓰고 두 앱 같은 규칙으로 언어를 고른다.)
- 줄 방향을 ML Kit 모서리에서 구한다. 1° 이상 기운 줄에는 방향을 따라가는 띠를 쓰고, 떨어져 인식한 가격·날짜 상자 앞 여백까지(그 사이의 읽지 못한 끝자리 포함) 띠를 덮는다. 같은 행에서 멀리 떨어진 다른 열 상자(수량 등) 앞에서도 멈춘다. 혼합 상자는 ML Kit 낱말 상자(`Line.elements`)로 번호 부분을 나눌 수 있으면 그 부분만 덮고, 나눌 수 없으면 줄 전체를 가리고 안내한다. 긴 줄 방향의 p90−p10 >3° 또는 추정 기울기 절대값 >20°, 가장자리 폭/글자 높이의 중앙값 >0.125 또는 가림 후보 줄 중 가장 흐린 값 >0.16, 글자 영역 휘도 p95−p5 중앙값 또는 가림 후보 줄 최솟값 <30이 현재 품질·각도 조건이다. 품질은 줄 모서리 네 점 안 픽셀로 잰다. 판정의 기대 동작은 공통 시험표(`apps/fixtures/masking/common-policy.json`)가 고정한다.
- 세로가 가로의 2배를 넘으면 1.5배 높이의 타일을 1/4씩 겹쳐 읽는다. 겹친 곳에서 두 번 읽힌 줄은 타일 경계에 잘리지 않은 쪽을 남긴다. 긴 사진은 짧은 변 1,500px·긴 변 9,000px까지 디코딩한다. 가림은 굽는 순간의 디코딩 크기로 OCR 좌표(0~1)를 투영하므로 이전 디코딩 규칙으로 저장한 초안도 같은 자리를 덮는다. 가림 확인 판정이 없던 예전 형식 제안은 확인 필요로 연다. 사본 재OCR은 가린 PNG를 앱 전용 초안 폴더의 숨김 임시 파일로 읽고 삭제한다. 이유와 지표는 기기 안 제안에 남긴다.

### 현재 iOS 구현

- Vision은 일본어·영어를 우선한다. 가나가 적은 사진에는 지원되는 한국어 인식 결과를 확인한다. (언어 선택은 superseded by [ADR-0013](0013-android-korean-ocr.md): 두 읽기를 모두 하고 Android와 같은 점수 규칙으로 고른다.) 자동 후보는 모서리와 여백을 따라 굽고, Vision에서 번호의 글자 범위를 얻은 혼합 상자에는 부분 가림을 쓴다. 그 범위를 얻지 못하면 상자 전체를 덮고 안내한다.
- 긴 줄 방향의 p80−p20 >4°가 각도 조건이다. 가능한 경우 민감 줄의 하위 3분위로 평가한 평활 휘도 p90−p10 <35 또는 경계 비율 <0.31이 현재 품질 조건이다. 세로가 가로의 2.5배를 넘으면 가로의 2배 높이인 타일을 가로의 1/4만큼 겹쳐 읽는다. 경계에서 겹치는 상자는 더 완전한 쪽으로 합치고, 한 타일에서만 읽힌 상자도 보존한다. 디코딩 긴 변은 3,000px까지다.
- 라벨 없는 예약 코드는 영문 1~4자와 하이픈 뒤의 숫자 5자리 이상을 가린다. 가격·품목 보호 상자와 같은 행의 상품 코드, JAN 번호, 자리 사이에 공백이 끼어 읽힌 날짜는 보존한다. 다른 조건으로 안내하지 않는 사본은 메모리에서 Vision으로 다시 읽는다. 정규화한 번호 전체가 4자 이상이면 위치와 관계없이 일치를 확인하고, 4자 이상 부분 일치와 3자리 숫자는 원래 가림 행 근처에서 확인한다.

두 앱에서 기준 가상 사진 12장과 변형 324장을 비교했다. 추가 열화·합성 사례의 구성은 Android와 iOS가 서로 다르며, 사본이 만들어진 사진을 대상으로 누락·과잉·안내를 집계했다. 임계값은 이 측정의 선택 결과다. 국소 퇴색·타일 경계·구버전 초안 좌표 등은 교차 검토에서 추가 확인 사항으로 남았다.

## 확인할 것

- 실제 기기의 VoiceOver·TalkBack 읽기 순서와 조절 동작, 실제 사용자 사진(긴 영수증, 기울어진 사진)에서 2% 띠가 충분한지.
- 사진 없는 직접 입력을 서버에 올릴 때의 요청 키와 중복 방지.
