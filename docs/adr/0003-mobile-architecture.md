# 모바일 앱의 기능과 서버 통신 경계

상태: accepted (2026-11-21)

iOS와 Android는 기능별로 코드를 묶고 화면 상태와 데이터 처리를 분리한다. 영수증 처리, 로그인, 서버 연결 중 하나를 바꿀 때 관련 없는 기능의 수정 범위를 줄이기 위해서다.

## 기능별 책임

- **영수증 가져오기**는 사진 수신, 기기 내 초안, OCR 대기열, 재시도와 마스킹 검토를 맡는다. 사용자가 확인한 가림 사본과 허용된 정산 필드만 여행방에 넘긴다. 원본과 OCR 전문은 기기에 둔다.
- **계정**은 [로그인과 기기 이전](0002-authentication-and-device-transfer.md)을 맡는다. 앱은 로그인 중 초대 정보를 보관했다가 인증이 끝나면 여행방 기능에 전달한다.
- **여행방**은 초대 수락, 구성원, 가린 증빙과 지출 동기화를 맡는다. **정산**은 분담 검토, 보류, 송금표 미리보기와 확정 결과 조회를 맡는다.
- 화면 상태는 iOS SwiftUI의 상태 모델과 Android Compose의 ViewModel로 관리한다. 앱 간 공유는 분담·반올림 같은 순수 계산부터 시작한다. 서버가 정산을 최종 확정하며, 미리보기와 서버 계산은 공통 예제로 비교한다.
- 기능별 폴더로 시작한다. iOS 본앱과 공유 확장이 함께 쓰는 가져오기 코드처럼 호출자가 실제로 여럿인 부분부터 빌드 모듈로 분리한다.

## 서버 통신

- 기능마다 필요한 동작을 인터페이스로 정의한다. 예를 들어 여행방은 초대 수락과 가린 증빙 등록, 정산은 검토에 사용한 버전으로 확정과 확정 결과 조회를 요청한다.
- Supabase SDK 호출은 구현체 내부에 둔다. 화면과 기능은 앱의 입력·결과 타입을 사용한다. 인증 세션을 다루는 경계와 여행방·정산 데이터를 다루는 경계는 각각 둔다. 앱 시작 지점에서 구현체를 연결한다.
- 자체 API가 생기면 필요한 동작부터 HTTP 구현체로 연결한다. 인증이 그대로라면 새 API에서 Supabase 세션 토큰을 검증하는 구성을 사용할 수 있다. 저장소·권한·기존 데이터의 이전은 서버 전환 계획에서 다룬다.
- 통신 구현체를 바꿀 때에도 비구성원 접근 차단, 같은 요청의 재시도에서 중복 방지, 오래된 버전의 정산 확정 거절을 동일한 시나리오로 확인한다.
